## Outcome and next review increment

For an existing local project P positively known to have deliberately deferred
exactly `contracts.evidence-freshness-policy/root` and never established governance
there, commit its first configuration G against the exact current deferred
outcome/relation D. Preserve P's Engine identity, physical root, v2 registration,
consumed initial choice, original instruction/request/D and all prior history.
The actual typed Rust SDK consumer can establish G, reopen P, resolve exact current
G and separately replay both original D and the establishment request.

Example: P's committed D has no configuration or ceiling. Later the human approves
the exact freshness configuration with a caller-supplied 7,200-second ceiling and
the supported standalone replacement terms. A configured agent submits that new
approved instruction, P/S and D's exact outcome/relation. It retains a complete
serialized locator before invoking the transition. Committed success separately
confirms validation, accepted advisory permission and exact cutover. After reopen
and actual SDK `Refresh(reset_state=true)`, current resolution returns G with that
same configuration, terms, rules and transition identity. Original D replay still
returns its original deferred outcome with replay delivery; it never restores D.

A second contender with a different configuration against the same D cannot
overwrite the winner. A stale D, already-established scope, ordinary setup root,
missing/corrupt history or uncertain earlier transition supplies no fresh
establishment opportunity. Activation grants no policy qualification, independent
evaluation, prior-result acceptance, governing assignment or action authority.

owner bookkeeping needed for truthful retry/history/currentness; no new Engine
initialization claim, root noncommit witness or universal operation ledger.

After exact read-only preparation, return a non-restorable prepared operation plus
complete serializable locator. Neither allocates identity nor mutates P. Restoring

generations, identity/anchor/registration, D's original committed terminal/claim
receipt, entire supported attempt lifecycle and exact current D bytes/identities.
Recheck immediately before the durable decision. Do not call ordinary setup or
registry/Context Resolution authority while holding governance locks; share locked
helpers instead of recursively acquiring public locks.

Append exact retained request/staged facts and intent, then one durable transition
commit decision bound to D before publishing any G current relation. Install
immutable configuration/rule/instruction/terms/outcome and predecessor-to-successor
facts, then replace `scope-current.json` only against exact D using prepared and
displaced relation bytes under the same locks. Close the exact installation,
current relation and terminal durably before reporting Committed. Readers cannot
return a usable G from the pointer alone or a usable D across unresolved attempt
evidence. A second request against D cannot commit after the first decision;
resolve/finish that decision before considering a new operation. There is at most
one established G and no replacement operation in this slice.

Original D terminal replay validates its immutable original closure and supported
inventory; it never calls a D-installation path after G. Current resolution validates
the entire applicable transition chain and exact terminal-selected current relation.
After committed G, replay D returns original D and current resolution returns G.
Terminal request replay never repairs a missing/damaged current relation. Recovery
of an incomplete decided transaction may finish only its exact retained decision.
