## Outcome and human checkpoint

An ordinary typed SDK caller can reopen a project, retrieve original truth, request
a deliberately fresh check or supply a permitted corrected captured input, and
complete a new occurrence under current applicable authority. Where the caller
cannot resolve an input-correction choice, it can carry an exact unresolved request
to the already authorized project agent and submit its approve, deny or clarification
decision. Native owners validate and retain that decision before any dependent
formation; a role, extra context, delivery or timeout grants nothing.

For illustration, the independently reviewed Packet-3 definition checks `amount`
against its original minimum. An original captured `amount: -1` remains a closed
Fail with its `/amount` violation. A caller-supplied correction to `amount: 125`
may produce a new current Pass under the same exact reviewed criteria if prior
terms permit it and all live checks succeed. Repeating that same capture deliberately
also forms a new occurrence and new Purpose-bound Engine issuance. Recovering any
original request key returns its original outcome, without a new check. Neither
correction nor repetition rewrites the earlier Fail or stale Indeterminate.

The exercised decision example is a correctable preformation refusal: the supplied
subject/case still names the old capture while the proposed input names corrected
content. Contracts refuses that inconsistency before allocating a Purpose. When
the caller leaves that correction choice unresolved, native preparation retains a
bounded `InputCorrection` request linked to the actual rejected candidate, missing
condition, old exact result and proposed consistent new input. The decision agent
named by the adopted prior-approved correction delegation may approve that
exact choice, deny it, or request clarification. Approval permits only the named
correction subject to fresh owner checks. A proposed wider path, altered schema,
weaker freshness rule or stale/revoked authority still refuses. The example supplies
no actual project actor, content, numerical policy, retention horizon or approval.

This packet delivers an independently meaningful correction/resolution workflow
and ends at its human result checkpoint. It is the last packet in this native/SDK
slice. Once its outcome and every slice acceptance condition are satisfied, meta
performs the single aggregate verification/review and slice closeout under the
[lifecycle](../../work-unit-lifecycle.md) and [review policy](../../review-and-closeout-policy.md).
The packet task returns PACKET_COMPLETE; it does not claim slice closeout. There is
no extra closeout packet, ledger or mandatory second commit.

## Selected owner and interface boundary

### Repeat, correction and live continuation

Reuse `prepare_local_evaluation`, `form_local_evaluation`, the complete owner
sequence and exact history/recovery APIs. A typed SDK workflow must distinguish
history, response recovery, deliberately fresh repeat, corrected capture and live
continuation. Proposed helper/type names are design, not existing API claims.
Do not use one ambiguous retry flag or silently select a new key after uncertainty.

Contracts validates a correction against the exact original closed result and its
retained input/definition, plus caller-supplied corrected captured content. Retain
a bounded additive lineage binding from that original result to the exact new
formation request/occurrence, with the selected action and any consumed decision
identity. Keep it in the existing owner repository and transaction machinery;
do not alter the old V3 snapshot/result preimages. Repeat with unchanged capture
reuses exact supported criteria and resolves fresh applicability. Correction may
change input only; changing schema, claims, permitted use, policies or dependencies
uses a separately justified, actually reviewed exact revision through existing
lifecycle APIs. No automatic relaxation, upgrade or result-fitted criterion.

Before collection commitment, unchanged fixed input may be reassessed under the
original issuance if the native owner accepts the new capability/currentness
observation. Retain earlier readiness observations. A committed basis cannot be
replaced; supported continuation only advances its exact existing frontier/set/
result chain. A known terminal is recovered, not reexecuted. An uncertain attempt
stays on its original locator until the owner resolves it; decision approval,
correction and new-key selection cannot masquerade as recovery or erase uncertainty.
An intentionally independent new check must be labeled as such and preserve that
unresolved history. A closed result is retrieval/delivery only. Changed capture,
requirements, applicability or Purpose always requires new formation and issuance.

  preserve earlier decisions. Clarification, silence and timeout permit no effect.

Contracts response is recovered by its original locator; recovery cannot create
an absent intent or allocate a second correction. Clearly distinguish noncommit,
committed, refused, still unresolved and uncertain durable outcomes.

admission held through Contracts' exact expected-state comparison/formation.
Resolve fresh v3 applicability before consuming guards, retaining existing lock
order. Declare every actual proof read and decision/Contracts write subtree before
effects; do not borrow broader initial paths over narrowed evaluation terms.
No global journey lock or cross-owner transaction is needed: durable acceptance,
fixed downstream request identity and exact owner recovery handle the two boundaries.

Reserved choices, unresolved material ambiguity or missing authority with no
supported resolution return an exact human-escalation need. A correctable in-scope
choice delegated to the named agent can use this path without another human
decision. Wider-path, Charter/terms replacement and other decision classes do not
gain positive consumption here; expose their truthful refusal/context and required
authority. No refusal authorizes scope expansion or its own new terms.
