## Outcome and next increment

For one freshly registered local project P, retain an explicit human-approved
instruction deliberately deferring exactly
`contracts.evidence-freshness-policy/root`. A real typed Rust SDK consumer can
commit that choice, reopen P, positively resolve its current deferred basis and
replay the original request after restart. No admission configuration is activated.
The instruction, exact scope, Engine identity, physical root, rule, original
outcome and current relation remain attributable and distinct.

Example: the human approves initiating P and deferring this admission scope as
part of the initial discussion. The caller retains the complete prepared locator
before invoking initialization. Success reports validation, accepted **advisory**
instruction and committed **deferral**, with no configuration binding. After a
lost reply the caller resolves that locator; after reopening it separately asks
whether this exact basis is current. An ordinary initialized project without
positive lifecycle history, or an established project with deleted active state,
cannot acquire deferral by calling this operation.

This is next for the selected **defer-first journey**. Positive applicability
resolution is the general prerequisite for dependent independent use. Under G4,
positive deferral, established non-applicability and satisfied applicable
qualification are alternative bases. This slice does not make deferral a mandatory
stage for every evaluation. The full forward journey remains adaptive intake →
complete independent checks → optional later governance on P → exact qualified
prior-result use → separately authorized action/commit. Only the scoped initial
choice and its truthful resolution are delivered here. Charter/posture, operating
delegation and later stages need their own supported owner outcomes; separate
owners alone do not require repeated human approval.

## Durable choice, current state and continuation

Select strict typed canonical JSON, bounded to 1 MiB per request/record, with the
Contracts canonicalization/fingerprint mechanisms and new v2 domain separators.
Typed decode must reject unknown/duplicate fields and trailing documents. The
[format standard](../../structured-data-format-standard.md) remains proposed;
this choice preserves Contracts JSON and existing owner contracts without adopting
its other defaults. There is no YAML authoring surface or editable human projection.

Use a distinct immutable `.handbook/admission-governance-project.v2.json` anchor
and `.handbook/admission-governance/v2/` owner inventory for **new v2 projects**.
Do not add v2 storage to an established v1 project or relax v1 inventory validation.
Separate stable registration from request history. Within v2, retain immutable
registration, exact shipped rule, request-addressed staged/intent/decision/installed/
terminal facts, original deferral and outcome, and an exact `scope-current.json`
relation closed by the committed transaction. The relation is a replaceable current
selection, not independently authoritative content: its expected bytes and identity
must match the terminal history. No scan for newest timestamps or missing-head
fallback may select a basis.

The committed initial-choice consumption means **the fresh initialization choice
was used**. It does not mean governance was established. The positive deferred
state means **this scope has never been established in its complete retained
lifecycle**; absence of a configuration cannot establish that proposition. Current
resolution validates complete history, identity, physical root, exact rule/scope,
terminal closure and expected relation under the owner lock. Historical resolution
uses the original exact request and returns its original outcome with replay delivery;
it does not select or restore the current relation.

The forward D→G contract is therefore credible without resetting registration:
the later operation must use the existing P/registration, compare the exact current
D outcome/relation as predecessor under the same lock, validate newly approved
configuration/terms and owner rule, and append one decided transition before
publishing its exact established current relation. D and its original request
remain immutable. Consumed, stale, already-established or uncertain predecessors
cannot qualify. Replay of D after G must still report original D while current
resolution reports G; replay never writes D back as current. A reader that lacks
support for a future transition version must refuse, not claim D is current.
These are forward contract obligations, **not tests of an implemented G API**.
This packet implements only the initial deferred transition and refuses unsupported
transition/inventory versions. It preserves the registration and immutable D facts
that a separately authorized continuation can use without data migration.

Keep later establishment separate. Source shows substantial additional validation,
exact predecessor/cutover and active-configuration work, but no requirement to
deliver it to make D usable. The shared record/transaction mechanisms can be reused.
Combining would give a runnable D→G proof sooner while enlarging this increment to
new establishment permission and races. No demonstrated duplicate transaction work
or unavoidable redesign currently justifies that expansion. If implementation
finds that the selected retention/identity contract cannot support continuation,
return the exact source-backed scope recommendation to human review before changing it.

Retain registration/claim, rule, instruction, deferral, outcome and recovery history
for the lifetime of this local project identity; no pruning, relocation, export or

Retain the inherited planning ceiling of 4,096 terminal requests without adding
