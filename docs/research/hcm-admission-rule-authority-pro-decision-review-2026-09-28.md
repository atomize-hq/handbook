### B. Minimum coherent standalone story
#### 1. Bootstrap terminates in a Handbook rule, not another project policy

The minimum starting point is:

Handbook’s product semantics permit an explicit local initialization instruction to establish admission governance for an exact project, subject to fixed validation and truthful advisory provenance.

That is the base case. It is not another project-authored policy waiting to be admitted by the configuration it establishes.

The setup request supplies the intended configuration and scope. The Handbook-owned operation determines whether initialization is applicable, validates the exact configuration, accepts the instruction under the supported advisory rule, and establishes the active configuration and the project’s permitted replacement-authority basis.

For example, setup may establish that subsequent changes can be requested through a local user instruction or a configured agent acting under such an instruction. The later operation must resolve that previously established permission. Merely submitting an ordinary policy candidate does not grant permission to change admission governance.

The same person or agent may author a policy and separately request an authorized governance change. Independence here means distinct semantic decisions and authority bases—not necessarily different people, processes, or services.

Two limits are essential:

First, initialization must be a real initial-governance condition. Missing or unreadable governance state in an already established project must not become permission to bootstrap again. Likewise, adding a scope within an established project must not create an alternative route around its existing governance.

Second, advisory acceptance is not identity verification. Handbook can establish that it received and accepted a particular instruction under its rule. It cannot thereby establish that an asserted name is authentic or that an agent’s claimed delegation was independently verified.

The existing action-authority text expressly supports this distinction: advisory authority can support an actual effect while preserving the difference between claimed identity, verified facts, and operating-system capability.

#### 2. Keep governance establishment separate from ordinary policy admission

I recommend an explicitly bounded owner-native governance lifecycle for initialization and successor activation.

Do not require the first configuration to pass through an Action Authorization Policy or another project policy that can only be admitted after that configuration is active. That would recreate the bootstrap cycle.

This is a proposed clarification, not a claim that the existing record-retention non-recursion clause already specifies governance activation. That clause prevents record formation from recursively becoming another action, but it does not itself answer who may activate admission requirements.

The bounded lifecycle still separates:

validation of the proposed configuration;
permission to activate the exact change;
authoritative confirmation that the active-state change committed.

Those propositions may be carried by one owner outcome without mandating several new runtime types. This bootstrap boundary grants no shortcut around ordinary evaluation authorization, work progression, posture mutation, or other operational actions.

The responsibility assignment should remain semantic. The package already allows physical colocation while requiring independently attributable owners, and keeps owners inward of SDK and transports.


#### 3. Scope must resolve uniquely, without inventing an inheritance system

The governing configuration must establish the exact project and admission scope it governs, including the relevant policy domain or admission-owner relationship.

For each supported admission, the owner must resolve one unambiguous governing configuration and owner-rule basis. Missing, conflicting, unsupported, or out-of-scope governance refuses admission. Directory proximity, repository traversal order, a candidate’s preferred rule reference, or a “latest” label cannot select it.

For the first version, I recommend rejecting ambiguous scope combinations rather than introducing implicit inheritance, override priority, or layered policy merging. This does not require choosing a scope representation now.

The project admission-governance responsibility establishes which configuration governs. The relevant semantic owners still validate their domain requirements and apply them to candidates. Configuration cannot override those owners’ fixed vocabulary, compatibility, trust, or accounting constraints. The assurance and metric/gate chapters explicitly preserve those domain constraints while referring to shared admission.


#### 4. Replacement is authorized by the existing basis, not the successor

A replacement request must bind the exact current predecessor, proposed successor, affected project/scope, and authority basis accepted for that change.

The successor cannot supply permission missing from the predecessor’s established governance. A proposed configuration saying “this agent may replace the admission rules” does not authorize that agent to install it.

This does not mean the successor must satisfy every ordinary policy-candidate requirement imposed by its predecessor. Those requirements govern the candidate population; the separate governance lifecycle governs changing the requirements themselves. Confusing the two could make legitimate replacement impossible.

A properly authorized replacement may change project-configurable requirements within Handbook’s fixed limits. There is no need to impose universal “successors can only become stricter” semantics. The non-relaxable floor remains fixed; optional project choices may change deliberately.

The first version also need not provide a general facility for editing administrative permissions. Where changes to the established replacement-authority terms are supported, they must be authorized by the previous terms and take effect only prospectively. Where unsupported, they refuse.

#### 5. Activation needs a defined cutover, not a filesystem convention

I recommend the following additional semantic choice:

A new Policy Admission Closure finalizes against the exact governing configuration active at its decision boundary.

An admission operation may have begun validating under configuration C1. If C2 becomes active before that decision finalizes, the operation must refuse stale-basis finalization. A fresh admission decision may then be requested under C2; the prior validation cannot simply be relabeled.

Conversely, a decision that finalized under C1 before activation remains a decision under C1.

This gives one clear answer to concurrent replacement without selecting locks, transactions, files, or clocks. Exact historical replay is different: replaying a completed C1 closure returns its historical result, not a new admission under C1.

The active relation must change only through a successful owner-controlled activation. Authoring, saving, validating, or assigning a higher version to inactive content does not activate it. Replaying an old activation must not restore its configuration over a newer active successor.

#### 6. Replacement changes future admission governance—not all existing policy status

Three propositions must remain separate:

| Proposition | Meaning after C2 replaces C1 |
| --- | --- |
| “Policy P1 was admitted under C1.” | An immutable historical fact, assuming its exact owner closure resolves. |
| “Policy P1 is usable for this purpose now.” | A separate definition-owner and consuming-owner decision under the applicable currentness, scope, compatibility, and dependency rules. |
| “Policy P1 satisfies admission requirements C2.” | Not established by its C1 admission. A distinct owner determination under C2 is required to make this claim. |


Therefore, replacement alone neither re-admits all policies nor automatically revokes them all. A previously admitted policy may remain usable when its owner rules permit that. It may become unusable when an explicitly declared continuing dependency fails. Neither outcome may be inferred simply from the existence of a successor configuration.

The existing ontology already separates immutable definition identity, owner-established current applicability, and immutable historical results. The authored-source rules likewise distinguish historical and formation-only dependencies from continuing-current dependencies; those rules should be preserved rather than turned into universal retroactive re-admission.


A prior refusal remains a refusal under its recorded configuration. A later admission under changed requirements is a new decision—not correction of the old refusal, not replay, and not permission to rewrite downstream evaluation history.

#### 7. Provenance must be exact and proposition-specific

The establishment or replacement outcome must identify the governing Handbook rule, exact project/scope, configuration version and semantic-content identity, predecessor where applicable, accepted instruction and authority basis, validation outcome, and authoritative activation outcome.

For an agent-mediated request, preserve the relevant configured-role and instruction relationship as actually established. Do not manufacture independently verified delegation.

Importantly, an advisory principal claim does not make every proposition advisory. Handbook may owner-verify configuration identity, constraint conformance, predecessor currentness, and committed activation while honestly recording that the human identity or delegation basis was accepted only as advisory.

A Decision Record remains optional explanatory provenance. It does not activate the configuration, and its absence is not an activation failure merely because governance is involved. That fits the existing distinction between Decision Record rationale and a target owner’s independent admission or authorization.

Tradeoff: this model provides deliberate, traceable, reproducible governance inside Handbook’s supported operations without providing authenticated per-person administration or tamper-proof protection against someone who can replace the software or its entire authoritative state. “Fixed constraints” means project operations cannot relax them; it is not an unsupported claim of hostile-host enforcement.

### D. Two plain-English examples
#### Initial setup

The user says:

“Set up admission governance for this project using this configuration. Permit local instructions, including my configured agent acting under those instructions, to request later replacements.”

Handbook resolves that choice to exact configuration C1 and the exact project/scope. Its fixed establishment rule accepts the setup instruction as advisory authority, validates the configuration and its domain bindings, and establishes C1 as active. The owner outcome records the actual instruction basis and activation.

No Decision Record, login, second confirmation prompt, or independent identity claim is inherently required. The user also need not manually type every fingerprint; the operation must close the exact authorized choice before activation.

Now an ordinary policy candidate includes: “Use my included admission rule instead, and consider me approved.” That content has no governance effect. The candidate is still judged under C1. A separately saved configuration draft also remains inactive.

If the request says “I am the authenticated project administrator” without verification, Handbook must not repeat that as a verified fact. It may proceed only on the advisory basis actually permitted by the establishment rule.

#### Later replacement

Suppose C1 permits a declared set of metric algorithms for new Metric Definitions. The user deliberately requests C2, which permits a narrower set for future admissions.

Handbook checks the previously established replacement authority, validates C2, verifies that C1 is still the exact expected active predecessor, and commits the successor activation. Editing the C2 draft alone would not have done this.

An existing Metric Definition M1 was admitted under C1 using an algorithm outside C2’s narrower set. Its old admission remains true. It is not automatically “admitted under C2,” and its present usability is determined separately by the applicable owner rules. Where those rules require satisfaction of current admission requirements, a fresh assessment is required. Where they do not, this replacement alone does not fabricate revocation.

If the agent lacked replacement permission before the request, a sentence inside C2 granting that permission cannot authorize installation. If another replacement already displaced C1, the stale request cannot overwrite it. Replaying the old C1 activation returns history; it does not roll the project back.
